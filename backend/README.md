## 数据库配置

1. 创建数据库 `fitness_diary`
2. 复制本地环境变量模板并填写真实值：

   ```bash
   cd backend
   cp .env.example .env
   ```

3. `.env` 已加入 `.gitignore`，不要提交该文件。Spring Boot 会在工作目录为 `backend` 时自动读取它，填写完成后可以直接启动：

   ```bash
   mvn spring-boot:run
   ```

通过 IntelliJ IDEA 启动时，请确认 Run Configuration 中的 Working directory 是项目的 `backend` 目录。也可以不创建 `.env`，而是把同名变量直接配置到 Run Configuration 的 Environment variables 中。

数据库连接使用 `FITNESS_DB_URL`、`FITNESS_DB_USERNAME` 和 `FITNESS_DB_PASSWORD`。图片上传使用 `FITNESS_OSS_ENDPOINT`、`FITNESS_OSS_ACCESS_KEY_ID`、`FITNESS_OSS_ACCESS_KEY_SECRET`、`FITNESS_OSS_BUCKET_NAME` 和 `FITNESS_OSS_IMAGE_DIR`。

### 登录配置

本地联调默认启用 `FITNESS_WECHAT_MOCK_ENABLED=true`，服务端会使用 `test_openid` 登录，因此可以继续查看当前测试用户的数据，不需要配置微信 AppSecret。

正式部署前必须配置并重启服务：

```properties
FITNESS_PRODUCTION_MODE=true
FITNESS_WECHAT_MOCK_ENABLED=false
FITNESS_WECHAT_APP_ID=真实小程序AppID
FITNESS_WECHAT_APP_SECRET=真实小程序AppSecret
FITNESS_AUTH_TOKEN_SECRET=至少32字节的随机字符串
```

小程序通过 `wx.login` 获取临时 code，只有服务端会接触 AppSecret 和 OpenID。业务接口统一从 `Authorization: Bearer <token>` 解析用户身份，不再接受客户端指定的 `userId`。

登录基础补强（2026-09-12）：微信身份到项目账户的映射统一由 `WechatAccountService` 完成。同一 openid 首次并发登录时，数据库唯一约束只允许一个账户写入；冲突请求会在独立注册事务结束后重新读取胜出的账户并正常签发 Token，不再向客户端暴露唯一键异常。已有用户不会重复创建，首次用户仍会获得默认身体档案和初始体重记录。正式环境设置 `FITNESS_PRODUCTION_MODE=true` 后，启动阶段会校验模拟登录已关闭、AppID/AppSecret 已配置且 Token 签名密钥不少于32字节；错误提示不会打印密钥内容。本轮不涉及数据库迁移。

自动化结果：登录补强完成时后端123项、前端65项全部通过；云托管阶段 A 加入健康检查、双传输、微信 TLS 故障诊断及网关身份登录后，当前基线为后端128项、前端69项全部通过。

单张图片的业务限制为 20MB（前后端共同校验）。`FITNESS_UPLOAD_MAX_FILE_SIZE` 和 `FITNESS_UPLOAD_MAX_REQUEST_SIZE` 只控制 Spring multipart 接收上限；提高这两个值不会自动提高业务限制。修改后需要重启后端服务。

OSS 应使用仅具备目标 Bucket 必要读写权限的 RAM 用户凭证，不要使用阿里云主账号 AccessKey。

### ID 使用约定

- `recipes.id`、`workouts.id` 是数据库自增主键，只允许在后端内部和子表外键中使用，不接收客户端传值，也不返回给小程序。
- `recipes.recipe_id`、`workouts.workout_id` 是业务 ID，小程序的详情、保存和删除操作统一使用它们。
- Java 子表实体使用 `recipeDbId`、`workoutDbId` 表示数据库外键，避免和业务 ID 混淆；数据库列名保持 `recipe_id`、`workout_id` 不变。

- 云模式登录优先使用 `wx.cloud.callContainer` 由微信网关注入的 `X-WX-OPENID`，并要求 `X-WX-APPID` 与服务端 `FITNESS_WECHAT_APP_ID` 完全一致；没有云网关身份头时才回退到 `jscode2session`。OpenID 不从请求正文接收，也不写入响应或日志。
- 云模式微信运动同步优先提交 `wx.getWeRunData` 返回的五分钟有效 `cloudID`，后端在确认网关注入的 OpenID、AppID 与当前账号一致后，通过云托管开放接口 `/wxa/getopendata` 换取步数。该路径不再调用 `jscode2session`，传统 `code + encryptedData + iv` 仅作为非云环境兼容回退；CloudID、OpenID 和开放数据原文均不写日志。
- 完整控制台配置和验收步骤见 `CLOUD_HOSTING_POC.md`。`config/runtime.js` 已切换为当前云环境，任何 AppSecret、数据库密码、AccessKey 或 Token/HMAC 密钥仍只能配置在云托管服务端。图片上传修复与正式上线衔接以项目根目录 `ITEM10_IMAGE_UPLOAD_AND_LAUNCH_PLAN.md` 为准。

## API接口

### 图片模块（第四项剩余优化，2026-09-05，用户已验证通过）

U0+U1（2026-09-19，U1 作为备选暂停）：

- 旧 `POST /image/upload` multipart 接口继续作为 legacy 回退；每次请求接受非隐私 `X-Upload-Attempt-Id`，日志只记录阶段、字节数、耗时和错误类别，不记录图片 URL、Object Key、Token 或临时凭证。
- `POST /image/upload-ticket`：JSON `{fileSize,format,uploadAttemptId}`，通过私有 `callContainer` 获取 60～600 秒的 OSS PostObject V4 Policy。服务端生成当前用户唯一 key；Policy 精确绑定 Bucket、key、声明大小、MIME、STS Token 和禁止覆盖字段，响应不包含 STS Secret。
- `POST /image/upload-confirm`：JSON `{ticketId,uploadAttemptId}`。服务端原子领取一次性 ticket，核对用户、有效期、OSS 元数据、实际大小、Content-Type 和前 12 字节魔数；成功后才返回 `imageUrl`。失败、过期及从未确认的 ticket 会尽力删除对应对象。
- ticket 状态持久化在 `image_upload_tickets`，支持云托管多实例用户隔离、过期和重复确认防护。已有数据库执行 `migrations/20260920_image_upload_tickets.sql`；全新空库的 bootstrap 已包含该迁移。
- 新增云端配置：`FITNESS_OSS_REGION`、`FITNESS_OSS_STS_ROLE_ARN`、`FITNESS_OSS_UPLOAD_TICKET_TTL_SECONDS`（默认 300）及清理间隔。RAM 调用身份只增加目标角色的 `sts:AssumeRole`，角色和每次 STS session policy 再限制 OSS 权限。
- 当前未实施 U2：编辑页实际上传继续走 legacy multipart。用户已确认代理上传与菜谱保存暂时可用，慢速主要与 VPN 和大图有关；不再要求 RAM/OSS 直传配置。U1 表和接口保留为以后出现可重复性能问题时的备选，不主动启用。
- 本轮控制台策略模板、环境变量和手工验收脚本见 `U1_OSS_DIRECT_UPLOAD_ACCEPTANCE.md`。

阶段 B 日志与告警（2026-09-20，等待控制台验收）：

- 云托管继续只采集 `stdout`；应用使用稳定关键词区分未知 5xx、数据库、微信登录上游、OSS、图片上传、后台任务、慢请求和慢 SQL。
- OSS 异步清理失败日志只记录稳定事件名和异常类型，不再输出完整图片 URL。
- 指标告警、日志关键词分组、通知测试和无害验收步骤见 `CLOUD_HOSTING_ALERTS.md`。未开通 CLS 时先完成内置云托管指标告警，不强制新增付费日志服务。

- `POST /image/upload`：multipart 字段 `file`，成功响应 `{ "code":200,"message":"success","data":{"imageUrl":"https://..."} }`。
- `POST /image/delete`：JSON `{ "imageUrl":"https://..." }`，统一返回 `{code,message,data}`。只允许删除当前用户未被菜谱引用的新上传图片；历史图片从所属菜谱移除并保存后由后端清理，不允许凭 URL 直接删除。
- 新图片存放在 `fitness-diary/images/{userId}/{uuid}.{format}`，历史无用户目录的 URL 不变，不需要执行 SQL。上传校验大小和图片文件头，设置正确 Content-Type，不接受 HTML/XML/SVG。
- 编辑页同时最多上传 2 张，后端实例最多处理 4 个 OSS 上传；单张客户端总等待上限 45 秒，OSS 连接 5 秒、读写等待 15 秒、请求上限 30 秒，不自动网络重传。SDK 参数依据：[阿里云超时配置说明](https://www.alibabacloud.com/help/en/oss/sample-code-for-timeout-and-retransmission-using-oss-java-sdk)。
- 上传过程中阻止重复选图、移除及保存；单张失败不丢失同批成功图片。返回页面会取消进行中的上传和待上传队列；已知 URL 的未保存图片尝试清理。
- 图片加载失败显示占位，可点击重试；不把 403、欠费、离线等加载失败当成文件不存在，也不自动删库。用户明确移除后保存才变更数据库。
- 旧图移除、删除菜谱的 OSS 清理仅在数据库事务提交后运行，最多两路后台清理，重查引用，不影响其他仍引用该图的菜谱。回滚不会删除 OSS 原图。
- 清理失败记录 `OSS_CLEANUP_PENDING`，不会将已提交的菜谱误报为保存失败。当前清理队列是有界内存队列，并非持久化任务；断电/强杀、上传已到 OSS 但响应丢失、或 OSS 长期停服可能留下孤立对象，需要后续人工核对或另行建设持久化重试。本轮没有扫描或删除 Bucket 内历史文件。
- 上传后若尝试保存但响应不明，退出时不会自动删这些图片，优先保证可能已保存的菜谱安全。

### 第五项：事务处理（用户已验证通过）

- 训练记录新增、修改和删除分别以整个 Service 方法为事务边界；训练主记录和动作明细一起提交，任何一步异常都回滚。修改时“更新主表→删除旧动作→插入新动作”不会留下半套数据。
- 菜谱写入显式使用 `@Transactional(rollbackFor = Exception.class)`；训练写入、每日饮食添加/移除采用相同回滚规则。菜谱、训练查询使用只读事务，写方法单独覆盖为可写事务。
- 审计日志使用独立事务（`REQUIRES_NEW`）。日志写入失败会记录 `AUDIT_LOG_WRITE_FAILED` 警告，不覆盖原业务异常，也不将已提交的业务操作误报成保存失败。失败的审计日志没有自动补写机制，仍需根据警告排查日志表/数据库问题。
- 第四项的图片清理仍在数据库提交后执行，回滚不删除旧图；数据库事务不能回滚 OSS 操作，不把两者当成同一个事务。
- 事务规则依据：[Spring 回滚说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html)。通过 Spring 注入的 Service 代理调用，不能用手动 `new ServiceImpl()` 代替；受检异常也按本项目规则回滚。
- 没有数据库结构变更、数据迁移或前端接口变更。本轮不处理第六项基础数据库接入、第七项营养快照/唯一约束，也不承诺阻止并发重复提交。

### R1：新用户引导与系统菜谱模板库

**问题定义：** 新用户首次进入食谱页时完全空白，必须从图片、食材和重量开始手工录入，首次使用成本过高，难以快速体验“饮食记录—热量分析”的核心闭环。

**结论：** 可以且建议在上线前实现。不要在注册时给每个用户复制一整套菜谱，而应建立只读的系统模板库，在空状态和“模板中心”按目标、餐次、热量区间等分类展示；用户可“一键加入今日饮食”或“复制到我的菜谱”后再个性化编辑。这样能减少重复数据，也便于以后统一修订模板。

**建议范围：** 首批准备约 12～20 个常见、步骤简单的模板，增加份量、适用目标、餐次、标签、过敏原提示、数据来源和版本字段。模板营养值上线前需人工复核，并明确按每份还是每 100 克计量。系统模板不得被普通用户直接修改或删除。

### R2：操作审计日志分级与减量

**问题定义：** 当前切面会将所有 Controller 调用写入 `operation_logs`，列表、详情和搜索等高频只读请求会快速放大日志量，降低真正风险事件的可见性，并增加数据库写入与存储压力。

**结论：** 可以且建议尽快优化。将“审计日志”“故障日志”“性能指标”分开处理：数据库审计日志只保留删除菜谱、删除训练、移除饮食、删除 OSS 图片、权限拒绝、管理端数据导入/修改等敏感或不可逆操作；普通 GET、搜索、正常登录和普通查询不再逐条落库。所有失败请求仍写服务端结构化日志，慢查询和慢请求继续保留告警。

### R6：微信运动与 Apple Health／Apple Watch 数据接入

**问题定义：** 用户希望减少手工录入，并优先使用手表或手机记录的真实活动消耗。

**结论：** 只能分级实现：

1. 微信小程序可通过 [`wx.getWeRunData`](https://developers.weixin.qq.com/miniprogram/dev/api/open-api/werun/wx.getWeRunData.html) 在用户授权后获取最近约 30 天的微信运动**步数**，但它不是 Apple Watch 活动热量接口，也不能保证识别具体设备来源。可以把步数同步为活动参考，并结合体重估算热量，但必须标注为“估算消耗”。
2. Apple Watch 会把活动能量写入 Apple Health/HealthKit；Apple 官方提供 `activeEnergyBurned` 类型，但读取 HealthKit 需要具备 HealthKit capability 的原生 iOS/watchOS 应用，并逐项取得用户授权。现有纯微信小程序无法直接调用这一原生能力。参考 Apple 官方的 [HealthKit 授权说明](https://developer.apple.com/documentation/HealthKit/authorizing-access-to-health-data) 和 [`activeEnergyBurned`](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/activeenergyburned)。

**推荐路径：** 第一阶段只接微信运动步数并明确估算口径；如果后续确认 Apple Watch 用户占比和产品价值足够，再单独开发原生 iOS 配套应用读取 HealthKit，并通过一次性绑定码与当前账号同步。健康授权必须可拒绝、可撤回、可删除，未授权或无数据时继续支持手工记录；不得把“没有返回数据”直接解释为用户没有运动。

**验收重点：** 授权拒绝不影响核心功能；同一天重复同步保持幂等；展示数据来源、更新时间和“设备值/估算值”；不得与手工训练消耗重复累计。

**本轮实现（2026-09-07，待用户验收）：**

- 第一阶段只接入 `wx.getWeRunData` 返回的最近 31 天微信运动汇总步数；不宣称能够读取 Apple Watch 活动热量、锻炼分钟、站立小时或具体设备来源。
- 新增 `GET /api/activity/wechat/summary`、`POST /api/activity/wechat/sync` 和 `DELETE /api/activity/wechat`。同步必须由用户点击触发，并使用同一轮 `wx.login` 的一次性 code 换取临时 `session_key`；后端校验解密数据的 AppID 水印和登录 openid，任何 code、密文、IV、sessionKey 均不保存、不写日志。

### R7：匿名人群百分位与脱敏训练排名

**问题定义：** 当有效用户数量足够时，希望展示当前训练、饮食或坚持度在相似用户群体中的相对水平；用户确认可增加经过严格脱敏的训练排名。

**结论：** 技术上可实现，但正式启用必须等待稳定样本量和统一统计口径。除匿名百分位外，可展示完成训练次数前10名；昵称按首尾保留方式掩码（如 `gordon → g****n`），次数降精度为区间，不展示原始昵称、账号身份、明细或精确健康数据。

**建议范围：** 只纳入达到最低完整度的活跃用户，按合理维度分组并设置最小群体阈值；样本不足时扩大分组或隐藏结果。后端定时生成匿名聚合分布，接口返回百分位、样本区间、统计周期及脱敏前10名。排名只使用完成训练次数，不使用热量、体重或计划完成率评价用户。

**测试数据方案：** 本地可以生成带固定随机种子、明确标记为 `SYNTHETIC` 的基准样本，优先放入独立测试表或测试环境，而不是向正式 `users` 表伪造用户。合成数据只用于验证分位算法、边界和 UI，不能与真实用户混合，也不能用于对外宣称真实排名。

**验收重点：** 样本不足时不输出虚假百分位；任何响应都不能反推出具体用户；合成数据脚本可重复执行和清理；同一统计周期结果稳定，周期切换后可解释。

**本轮实现（2026-09-08，用户已验证通过）：**

- 新增 `GET /api/comparison/training`，固定汇总最近30个业务日期。只比较完成训练次数、按日期去重的实际训练天数和计划完成率；热量保留在内部样本结构中但不作为排名指标，避免把不同体型或训练方式的消耗高低解释为优劣。
- 优先选择相同健身目标的活跃样本；同目标少于默认阈值10人时扩展到全部目标，整体仍不足阈值则返回 `POPULATION_INSUFFICIENT` 且所有百分位为 `null`。当前用户近30天无训练时返回 `CURRENT_DATA_INSUFFICIENT`，不把缺失记录排名为最低。
- 百分位采用“达到或超过”的平分口径：样本指标小于或等于当前值的人数除以样本总数，四舍五入为0～100整数。脱敏榜单按完成训练次数降序并采用并列名次，最多返回10行；当前用户单独显示大致名次，他人昵称保留首尾字符并用 `*` 替代中间字符，次数只返回 `0 / 1–4 / 5–8 / 9–12 / 13–16 / 17–20 / 21以上` 区间。接口不包含原始昵称、participant key、openid、用户 ID 或他人精确值。

### 用户模块
- `POST /user/login` - 使用微信临时 code 登录（唯一免登录接口）
- `GET /user/me` - 获取当前用户信息
- `POST /user/update` - 更新用户信息
- `POST /user/get-daily-calories` - 计算每日推荐摄入量

### 菜谱模块
- `GET /recipe/list` - 获取当前用户的菜谱列表
- `GET /recipe/catalog?keyword=&goal=&page=0&size=20` - 分页搜索“我的菜谱 + 只读系统模板”，支持减脂/增肌分类，全部列表中用户菜谱优先
- `GET /recipe/get/{recipeId}` - 获取单个菜谱详情
- `POST /recipe/save` - 保存菜谱
- `DELETE /recipe/delete/{recipeId}` - 按业务 ID 删除菜谱

### 健身模块
- `GET /workout/list` - 获取当前用户的健身记录列表
- `GET /workout/get/{date}` - 获取当前用户指定日期的健身记录
- `POST /workout/save` - 保存健身记录
- `POST /workout/complete/{workoutId}` - 将已到期训练计划确认完成并写入实际消耗
- `POST /workout/cancel/{workoutId}` - 取消训练计划但保留记录
- `DELETE /workout/delete/{workoutId}` - 按业务 ID 删除健身记录

### 对比模块
- `POST /compare/get-daily-data` - 获取每日热量对比数据
- `POST /compare/add-recipe` - 添加菜谱到今日饮食
- `POST /compare/remove-recipe` - 从今日饮食移除菜谱

### 数据库模块
- `GET /database/food/list` - 获取食物数据库列表
- `GET /database/food/get/{foodName}` - 获取食物详情
- `GET /database/food/search?keyword=&page=0&size=20` - 分页模糊搜索食物
- `POST /database/food/resolve` - 按名称批量解析已有食材，JSON `{ "names": ["鸡胸肉"] }`

- `POST /database/exercise/resolve` - 按名称批量解析已有动作，JSON `{ "names": ["深蹲"] }`
